## D3. Monorepo setup follows the current Expo guide (2026-10-19)

From the Expo monorepo guide (docs.expo.dev/guides/monorepos, examples on SDK 58):

- pnpm workspaces with `apps/*` and `packages/*` in `pnpm-workspace.yaml`.
- Expo configures Metro for monorepos automatically from SDK 52 through `expo/metro-config`, so no `watchFolders` or `nodeModulesPaths` overrides.

## D4. Accessibility lint plugin under ESLint 9 (decided 2026-10-20)

SCOPE.md section 10 asks for `eslint-plugin-react-native-a11y`. Its latest release (3.5.1) declares support only up to ESLint 8.

Decision:

- **ESLint 9.39, not 10.** `eslint-config-expo` 58 depends on `eslint-plugin-react` and `eslint-plugin-import`, which support ESLint up to 9. ESLint 10 would leave those unsupported.
- **The a11y plugin is kept**, wrapped with `fixupPluginRules` from `@eslint/compat` for flat config. A probe file confirmed its rules fire: a touchable with no role or label fails `has-valid-accessibility-descriptors`, and an invalid role fails `has-valid-accessibility-role`.
- The `all` rule set is enabled for `.tsx` files in `apps/mobile`, `packages/ui` and `packages/sprites`, except `has-accessibility-hint`: hints are optional context, while the scope requires roles and labels.

## D6. Workspace scaffold choices (2026-10-20)

- **pnpm 12 supply-chain policy kept on.** pnpm 12 refuses packages published within its minimum release age. Rather than adding `minimumReleaseAgeExclude` entries, Expo ranges are written as `~58.0.0` so pnpm picks the newest patch old enough to pass. Today that resolves `expo` 58.0.14 and `expo-router` 58.0.23, one or two patches behind what `expo-doctor` expects; the next `pnpm update` after the cutoff passes picks up the newer patches.
- **Routes live in `apps/mobile/app/`** and other app code in `apps/mobile/src/` with the `@/` alias, as SCOPE.md section 10 lays out. Current Expo templates default to `src/app/`; both are supported.
- **App config is `app.config.ts`** (typed, and able to read env vars later) instead of the template's `app.json`.
- **Workspace packages ship TypeScript source** (`main: src/index.ts`). Metro transpiles them in the app; nothing is prebuilt.
- **`react-dom` peer warning:** `expo-router` pulls `react-dom` 19.3.1 as an optional peer, which wants `react` ^19.3.1 while SDK 58 pins `react` 19.3.0. The app does not target web, so this is a warning only.
- The template's `LICENSE` (Expo's MIT notice for the template), `AGENTS.md` and `.claude/settings.json` were removed: the repo's own licence is the owner's decision and `CLAUDE.md` covers agent guidance.

## D7. Dependency build scripts stay off (2026-10-20)

pnpm 12 does not run dependency install scripts unless they are approved in `pnpm-workspace.yaml` (`allowBuilds`). Two packages asked and were denied, because both ship prebuilt native binaries and their scripts are only a fallback that compiles from source: `unrs-resolver` (used by the ESLint import resolver) and `@parcel/watcher` (used by Jest's file watcher). Any future approval gets its own entry here.

## D8. CI pipeline (2026-10-20)

- `.github/workflows/ci.yml` runs on every pull request and every push to `main`, with two jobs: **`ci`** (frozen-lockfile install, lint, type-check, tests) and **`gitleaks`** (secret scan of the full git history). Both are meant to be required checks on the `main` ruleset.
- Third-party actions are pinned to commit SHAs with the release named in a comment, so a moved tag cannot change what runs. Releases at least two weeks old were chosen (checkout v7.0.0, setup-node v7.0.0, pnpm/action-setup v6.0.10, gitleaks-action v3.0.0).
- The workflow token is read-only (`contents: read`). Gitleaks PR comments are off because they need a write token; a finding still fails the job.
- Deferred from SCOPE.md section 13.2: coverage reporting arrives with the first real `game-core` code in P1, and the second job that starts the local Supabase stack arrives with the Supabase setup PR.

## D9. Local Supabase setup (2026-10-20)

- **The Supabase CLI is a pinned workspace dev dependency** (`supabase` 2.120.0 on npm), run through `pnpm exec supabase` or the `pnpm supabase:*` scripts. Local machines and CI therefore use the same version, instead of whatever Homebrew has installed. The npm package has no install script, so D7's build-script policy is unaffected.
- **Docker runtime:** OrbStack on the owner's Mac. CI uses the Docker on GitHub's Ubuntu runners.
- **`supabase/config.toml` changes from the defaults:** `project_id = "habit-rpg"`; Storage turned off because the app stores no files; Auth `site_url` and redirect URLs set to the app scheme `habitrpg://`. Email sign-in uses 6-digit codes (the CLI default `otp_length = 6`), matching SCOPE.md section 9.5.
- **CI:** a third job, `supabase`, starts the stack without the services the tests don't need, then runs `supabase db reset` so every migration and the seed are applied from scratch on each PR. pgTAP and Deno tests join this job in P3.
- **Hosted project:** not created yet. When it is, it goes in region `ca-central-1` (D1), and only its URL and publishable key go in the app (`.env.example`).

## D10. Game-core rule details the scope leaves open (2026-10-20)

SCOPE.md section 3 gives the formulas; these are the choices where it does not say exactly how.

- **Bad habits ignore difficulty.** The difficulty table lists "Bad habit" as its own row (5 XP, 2 gold, 8 HP), so a "don't" quest always uses those values, even though the habit row still stores a difficulty.
- **Crit hash is 32-bit FNV-1a** over the completion id's UTF-16 code units (`Math.imul`, unsigned). It is tiny, has published test vectors (checked in the tests), and gives identical results in Hermes and Deno.
- **Integer arithmetic for rewards.** `xp` is computed as one integer fraction, `base * streak% * (200 + INT) * bonus% / (100 * 200 * 100)`, then rounded halves-up; boss damage the same way. This avoids floating-point drift such as `10 * 1.05` landing just under or over `.5` on different engines.
- **Gear XP bonuses multiply last.** The Wizard Hat's "+10% XP on Mind habits" multiplies the XP after the streak and INT bonuses.
- **Rounding on faint:** gold lost is `floor(gold * 25%)` and HP returns at `floor(max_hp * 50%)`.
- **Late completions** skip the streak multiplier entirely (multiplier 1.0); INT and gear bonuses still apply.

## D11. Dates, streaks and day close in game-core (2026-10-20)

- **Time zones use the built-in `Intl.DateTimeFormat`, not a date library.** SCOPE.md section 7 suggests `date-fns` v4 with `@date-fns/tz`, but section 3 makes `game-core` dependency-free. `Intl` with an IANA `timeZone` works in Node, Deno and Hermes, so `game-core` keeps zero dependencies. Calendar arithmetic (adding days, weekdays) runs on plain dates through UTC, which has no daylight saving. This still needs one check on a real Hermes build in P2 (Expo Go ran the placeholder fine, but no time-zone code yet); if Hermes misbehaves, the fallback is `@date-fns/tz` in the app only.
- **Tested zones:** `America/Los_Angeles` and `Pacific/Auckland`, including both 2026 daylight-saving changes in each, and one instant that is a different date in each zone (SCOPE.md section 13.1, test 5).
- **Scheduling:** `daily` habits run every day whatever their bitmask; `weekdays` habits and "don't" quests follow the bitmask (Monday = 1 … Sunday = 64, all days = 127).
- **The global streak changes at day close:** +1 for a day with any completion, reset to 0 for a day with none. The longest streak never shrinks.
- **A habit's own streak** counts back from today, skipping unscheduled days; if today is scheduled but not done yet, it counts from yesterday, since today is still open.
- **Oak Shield** ("blocks the HP loss of 1 missed daily per day") blocks the costliest missed habit that day; a broken "don't" quest is a slip, not a missed daily, so it is never blocked.
- **A habit counts on day D** if it was created on or before D and not archived or deleted on or before D.
- **A user's first day close** starts from their sign-up date (`firstDate`); later runs start the day after `last_closed_date`, which covers job outages.

## D12. Gear, bosses and golden vectors (2026-10-20)

- **Gear ids** are kebab-case slugs (`iron-sword`, `oak-shield`, `wizard-hat`, `leather-boots`, `lucky-clover-charm`, `dragon-cape`); these are what `inventory.item_id` will store. Each of the six items has its own slot, so equipping one replaces only an item in that slot.
- **The shop's disabled reasons** come from `canBuy`: `owned`, `locked` (with the unlock level) or `insufficient_gold` (with the gold still needed), matching the "Unlocks at level N" and "Need N more gold" captions in SCOPE.md section 5.2.
- **The boss roster wraps:** after Monday, the final boss, the next week starts again with the Procrastination Slime.
- **A defeated boss stays defeated** when a member undoes a completion. SCOPE.md section 9.4 says an undo gives the damage back, but taking back a victory after members may have claimed the +50 gold would be confusing and could double-pay; undoing still refunds damage while the boss is alive.
- **Party codes** are generated from a caller-supplied random source (the server passes a crypto RNG), keeping `game-core` free of randomness so it stays deterministic and testable.
- **Golden vectors** live in `packages/game-core/golden/vectors.json`. Every expected value is worked out by hand from the formulas (each case names its arithmetic), not produced by running `game-core`. Vitest checks them now; the Deno Edge Function tests load the same file in P3.

## D13. UI foundation (2026-10-20)

- **Fonts load with `useFonts` in the root layout**, holding the splash screen until they are ready. This is the method that works in Expo Go; the `expo-font` config plugin (fonts embedded at build time) only works in development builds, so it can replace this once the app moves to one. If fonts fail to load, the app continues with system fonts rather than staying on the splash screen.
- **Versions added:** `@expo-google-fonts/pixelify-sans` and `@expo-google-fonts/inter` 0.4.2, `expo-font` 58.0.8, `expo-splash-screen` 58.0.10, `react-native-reanimated` 4.7.1, `react-native-worklets` 0.13.0 (all via `npx expo install`).
- **`packages/ui` is a React Native package:** `react`, `react-native` and `react-native-reanimated` are peer dependencies (the app provides them) and dev dependencies (for its own type-check and tests). It has its own Jest config with the `jest-expo` preset.
- **Reanimated under Jest uses a small hand-written mock** (`packages/ui/jest.setup.js`, shared by the app's Jest config). Reanimated 4.7's own mock imports the native module and fails, and its web resolver needs `react-native-web`, which this app does not use. The mock covers only the APIs `packages/ui` uses and jumps animations to their final values; extend it when a component uses more.
- **Reduce Motion** comes from `useReduceMotion()`: the system setting, unless the in-app override (`ReduceMotionProvider`, set from Settings in P2) forces it on or off. Animated components skip straight to the end state when it is on.
- **Progress bars expose `accessibilityValue={{ text: "42 of 50" }}`**: the accessibility lint rule allows numbers or text, not both, and the text form reads naturally.
- **The gallery** is the route `/dev/gallery`, linked from the home screen only in development and redirecting home in production builds.

## D14. Game components (2026-10-20)

- **`react-native-svg` 15.16.0** is added (via `npx expo install`) for the pixel check mark and, next, the sprites.
- **No `shapeRendering="crispEdges"`.** SCOPE.md section 5.2 asks for it on sprites, but `react-native-svg` has no such prop. Pixel art stays sharp on native as long as every cell is a whole-unit `Rect` drawn at a whole-number scale, so sprites will be drawn that way. The design canvas's check-mark path also traced over itself and filled almost nothing, so the check is drawn as a 7 × 7 grid of 2-unit cells instead.
- **HabitRow** is a `checkbox` with its checked state exposed, a label that reads like the SCOPE.md section 5.10 example, and an "Edit" screen-reader action alongside long press. It is memoised for long lists.
- **ShopItem's states come in as data** (`buyable`, `expensive` with gold needed, `owned`, `equipped`, `locked` with unlock level), matching `canBuy` in `game-core`. A too-expensive item keeps its effect text and adds "Need N more gold" after it.
- **Heatmap input** is 84 daily counts, oldest first, one Monday-to-Sunday week after another. The grid is a single accessible image described by a summary sentence; the Less/More legend is hidden from screen readers because the summary already says it.
- **Numbers like "1,240"** are formatted with a small helper rather than `toLocaleString`, so they look the same on every device whatever its locale.
- **Testing:** React Native Testing Library 14 makes `fireEvent` async, so every call is awaited; overlapping ones break the following tests. ESLint now resolves each workspace's tsconfig paths, including the app's `@/` alias.

## D15. Overlays and form controls (2026-10-20)

- **Modal and BottomSheet wrap React Native's own `Modal`** (fade for dialogs, slide for sheets, no animation when Reduce Motion is on) rather than adding a bottom-sheet library; the app's sheets are short forms that don't need drag-to-resize. If the habit sheet later needs gestures, `@gorhom/bottom-sheet` is the candidate and gets its own entry here.
- **Screen readers can always close an overlay:** both mark themselves modal (`accessibilityViewIsModal`), which hides the tap-outside backdrop from VoiceOver, so both also handle the VoiceOver escape gesture (`onAccessibilityEscape`); Android's back button closes them through `onRequestClose`.
- **Toast** is presentational: the message is a polite `alert`, an optional action (Undo) sits beside it, and it calls `onDismiss` after 5 seconds (SCOPE.md section 5.6). Which toast is showing will live in the Zustand UI store in P2.
- **SegmentedControl** is a `tablist` of `tab`s with the selected one announced; each segment is at least 44 pt tall. **TextField** shows a character count when it has a `maxLength`, and an error replaces its hint and is announced.
- **`react-native-safe-area-context`** is a peer dependency of `packages/ui` (the sheet pads above the home indicator); its own Jest mock reports zero insets.
- **`StyleSheet.absoluteFillObject` is gone in React Native 0.88**; use `StyleSheet.absoluteFill`.

## D16. Sprites (2026-10-20)

- **One shared palette, character keys.** Every sprite is an array of equal-length strings; each character is a key into one palette (`packages/sprites/src/palette.ts`) and `.` is transparent. This is the scope's "palette-index matrices" in a form that is easy to read and edit as text. Tests check every matrix's size (heroes and gear 10 × 12, bosses 12 × 8) and that every character is in the palette.
- **The Knight and the Procrastination Slime are copied cell for cell from the design canvas**; the Mage, Rogue, six gear overlays and seven other bosses are original art in the same chunky style. Nothing is third-party, so `docs/ASSETS.md` gains no rows. The canvas Knight uses 8 colours with no separate outline colour; the art follows the canvas rather than the "3 to 5 colours" line in SCOPE.md section 5.2.
- **Heroes have no weapon of their own.** The canvas Knight holds a sword; here the sword is the Iron Sword overlay, so equipping and unequipping it changes the sprite as F5 requires.
- **Gear layers:** capes draw behind the hero, everything else in front, in shop order.
- **Rendering:** each sprite is one SVG whose `viewBox` is in cells, so every rectangle sits on whole units; neighbouring same-colour cells in a row merge into one rectangle (a sprite draws about 30 rectangles instead of 120). The on-screen cell size should be a whole number of points.
- **A defeated boss** is drawn in greys of the same brightness and its accessible name says "defeated"; the visible "Defeated!" label is on the BossCard.
- **`HeroClass`** (`knight` | `mage` | `rogue`) now lives in `game-core`, next to the other domain types.

## D17. Local database (2026-10-20)

- **Versions:** `expo-sqlite` 58.0.13 (via `npx expo install`), `drizzle-orm` 0.45.4 and `drizzle-kit` 0.31.11. The Drizzle Expo guide currently shows its 1.0 release candidates (`@rc`); the stable 0.45 line is used instead, and moving to 1.0 gets its own entry once it is stable.
- **Setup follows the Drizzle Expo guide:** `drizzle.config.ts` with `driver: 'expo'`, `babel-plugin-inline-import` so the `.sql` migration files are bundled as strings, `.sql` added to Metro's source extensions, and `useMigrations` in a `DatabaseGate` that holds the first screen until migrations finish. The database opens with `enableChangeListener: true` so `useLiveQuery` can repaint screens after writes.
- **Migrations** are generated with `pnpm --filter @habit-rpg/mobile db:generate` into `apps/mobile/src/db/migrations` (ignored by lint and Prettier because drizzle-kit writes them). Never edit a generated migration; change the schema and generate a new one.
- **Schema:** mirrors SCOPE.md section 8.1 for `profiles`, `characters`, `habits`, `completions` (with the partial unique index allowing one active completion per habit per day), `day_closures`, `inventory` and the party read-models, plus the local-only `outbox`, `sync_state` and `settings` from section 8.2. Two additions the server schema will need in P3: `habits.created_date` (day close must skip days before a habit existed, D11) and display fields on `party_members` (hero name and class, so the Party screen works offline).
- **Queries are synchronous** and take an `AppDb` type (`BaseSQLiteDatabase<'sync', …>`) that both expo-sqlite and sql.js satisfy. Synchronous writes keep a habit completion inside one SQLite transaction with no awaits, which helps the 100 ms target.
- **Query tests run on sql.js** (SQLite compiled to WebAssembly) in a separate plain-Node Jest project, with the real migrations applied. That tests the same SQL as the phone without native modules or build scripts. jest-expo's runtime polyfills broke sql.js's async start-up, hence the separate project.
- **Demo seed** (`seedDemo`) replaces all local data with the design canvas's hero (Sir Commit, level 7, 12-day streak), the five sample quests with 12 weeks of history, two gear items and a four-member party fighting the Procrastination Slime. It takes `now`, the time zone and an id generator, so tests are deterministic.
- **`esbuild`'s install script is denied** like the two in D7; drizzle-kit runs fine on its prebuilt binary.

## D18. App shell and route guards (2026-10-20)

- **Route groups follow SCOPE.md section 5.3:** `(auth)/sign-in`, `(auth)/onboarding`, `(tabs)` with Quests (`index`), Party, Hero and Stats, and the dev-only gallery. Expo Router's `Stack.Protected` guards decide which group is reachable; a pure `decideArea` function holds the rule (no session and no demo → sign-in; no hero yet → onboarding; otherwise the tabs) and is unit-tested.
- **The guard reads the database synchronously on the first render**, then re-reads after every change through expo-sqlite's `addDatabaseChangeListener`. Drizzle's `useLiveQuery` returns empty data on its first render, which made the guard pick sign-in for one frame and then switch, and Expo Router logged a `ROUTE_NAMES_CHANGED` error while the tabs were mounting.
- **Until P3 there is no real sign-in:** the sign-in screen shows the email field with "Send code" disabled and a note, and "Try the demo" seeds the demo hero. A temporary "Leave the demo" button on the Stats tab returns to sign-in until Settings (with Sign out) exists. The onboarding route is a placeholder until its own PR.
- **Tab bar:** four equal tabs with the design canvas's outline icons (square, circle, shield, axis), gold when active and muted otherwise, labels always shown, 60 pt plus the bottom safe area (84 on an iPhone with a home indicator). The tab-change haptic from section 5.9 waits for the P6 polish pass with the other haptics.
- **`expo-crypto` 58.0.7** supplies UUIDs for new rows (`newId`); the device time zone comes from `Intl.DateTimeFormat().resolvedOptions().timeZone`.

## D19. Playing without an account (decided by the owner, 2026-10-20)

- **"Start without an account" on the sign-in screen** creates a real local hero through onboarding. It changes the scope slightly: SCOPE.md F1 assumes email sign-in comes first. The owner chose it so a player can use the full app in P2 before the backend exists, and it keeps the app usable fully offline from the very first launch.
- **How it works:** the button sets `settings.local_only`, which the route guard treats like a session, so it opens onboarding (name, class, time zone). `createHero` writes a level 1 hero with 44 HP and no gold under the local user id, replaces any leftover demo data, and marks onboarding done, which opens the tabs. The flag needed migration `0001_add_local_only_setting`.
- **In P3** signing in will attach this local hero and its history to the new account and upload it through the sync outbox, instead of starting over. That flow gets its own entry when it is built.
- **Onboarding validation** uses Zod in the app: hero names are cleaned (whitespace tidied, control and invisible characters removed, SCOPE.md section 9.6) and must then be 2 to 20 characters; the time zone must be one `Intl.DateTimeFormat` accepts. The device's zone is pre-filled and can be changed. `react-hook-form` (SCOPE.md section 7) is left for the habit sheet, which has more fields; three single-field steps don't need it.
- **"Reset and sign out"** on the Stats tab (temporary, until Settings exists) wipes all player data and returns to sign-in, for the demo and a local hero alike.
- **The "Your adventure begins" animation** at the end of onboarding (section 5.8) waits for the P6 animation pass; finishing goes straight to the tabs for now.
- **Layout fix:** with `behavior="padding"`, `KeyboardAvoidingView` replaces its own bottom padding with the keyboard height, so the safe-area padding moved to an inner view (`KeyboardScreen`). Before that, the bottom buttons on sign-in sat over the home indicator.

## D20. Quests screen and completing habits (2026-10-20)

- **PR order changed within P2:** this PR is the Quests screen plus completing and undoing habits (the core of F3), and the habit sheet (F2) is the next PR. A Quests screen whose quests can't be ticked isn't usable, while the demo already has habits to tick. The level-up and faint modals, the floating "+20 XP" animation and the haptic come with the next F3 pieces.
- **Screens read with `useDbQuery`:** a synchronous query on the first render, then again after every database change (expo-sqlite's change listener). Completing a habit repaints the screen right after its transaction with no loading state, and the route guard now uses the same hook (D18).
- **Completing a habit** runs in one SQLite transaction: insert the completion with the rewards from `game-core` (streak, INT, Wizard Hat bonus, deterministic crit seeded by the new completion's UUID), then apply the XP with `applyXp` (level-ups refill HP and add 25 gold) and add the gold. A second completion of the same habit on the same day is ignored, matching the database's partial unique index. Max HP is re-derived after the insert, so a new CON point counts straight away.
- **Undo** marks the completion `undone_at` (never deleted, SCOPE.md section 8.3) and takes back its XP and gold; XP clamps at 0 in the current level, the level never drops, and the 25 gold from a level-up is kept.
- **The reward shown on an open quest** is the XP that completing it now would give (section 5.4); only gold changes on a crit, so the preview needs no completion id.

## D35. The sync contract (2026-10-23)

- **The plan for `sync`, agreed with the owner:** five PRs. (A) this contract; (B) the function's skeleton: auth, limits, the database connection, pulling changes and creating the server hero on first push; (C) pushing habits and completions, with the server recomputing every reward and a replay test; (D) gear purchases and profile edits; (E) a one-time import of a linked local hero. ## D36. The sync function's skeleton (2026-10-23)

- **`supabase/functions/sync`** (sync PR B of D35): authentication, limits, one transaction per sync, pulling changes, and the first push creating the server profile and hero. Habits, completions and gear follow in PRs C and D; until then a request carrying them is refused whole with 501, before anything is written.
- **Authentication** uses Supabase's `@supabase/server` 1.9.1 (`withSupabase({ auth: 'user' })`, the pattern its docs now recommend, on top of the platform's `verify_jwt`). The user id comes only from the token's claims, never from the body.
- **Database access** is Postgres.js 3.4.9 on `SUPABASE_DB_URL`, which the local runtime provides (checked with a temporary probe function), with `prepare: false` and one connection per function instance. Every sync runs in one transaction that first takes a per-user advisory lock (`pg_advisory_xact_lock`), so two syncs for the same player take turns; a row lock wasn't possible because the hero row may not exist yet. `server_time` is the database's `now()`, the same clock that stamps the rows.
- **Limits and errors:** a body over 256 KB gets 413 before parsing; invalid JSON or a request that fails the contract gets 400 with only paths and codes (`changes.0.data.hero_name: too_small`), never the values, since payloads hold habit names; unexpected errors get 500 and are logged without the payload (SCOPE.md section 9.6).
- **Pulling:** each synced table is queried for the player's rows above the cursor (one more than a page each), merged by `server_seq` and cut at 500, with `has_more` and the new cursor. Dates and times are cast to text in SQL and timestamps sent as ISO strings, matching the contract. The hero comes back separately as `character`; before the first push it reads as game-core's new hero.
- **The first push** inserts the profile and the hero with game-core's `newHero()` values; later profile pushes update name, class and time zone, and never touch the hero.
- **Tests:** Deno integration tests call the running function over HTTP on the local stack, with a fresh confirmed user each (created and deleted through the auth admin API): no token, bad requests, the first push, cursor and paging (501 rows for each of two players: 500 then 2 come back, all of them A's), and refusing unsupported changes whole. `pnpm functions:test` writes the stack's local URLs and default keys to `supabase/.temp` (ignored by git and outside the function watcher) and skips these tests when the stack isn't running.
- **Local runtime quirk:** under `supabase start`, the runtime's `SUPABASE_DB_URL` points at `supabase_db_<project>`, and Deno's resolver refuses the underscore (`ENOTFOUND`); under `supabase functions serve` the host is `db` and it works. CI therefore starts the stack without its edge runtime, runs `supabase functions serve` in the background and waits for a 401 from `sync` before the tests. The hosted project's URL doesn't have the problem. The edge runtime is 1.77.4 (Deno 2.1.4 compatible), older than the Deno 2.9.7 the tests use, so the function sticks to features both support.
- **pgTAP schema tests are now scoped to their own user,** because a local database used for function tests already holds other players' rows.

## D37. Pushing habits (2026-10-23)

- **Sync PR C is split in two** to keep each reviewable, as warned when it started: C1 (this) pushes habits; C2 pushes completions with server-recomputed rewards, the hero event log and the replay test. Completions are much larger (duplicates, undo, late days, server stats, events).

## D38. Pushing completions and the hero's event log (2026-10-23)

- **Sync C2:** `sync` now applies completions, with the reward worked out on the server from its own data, which makes the server the authority over the hero (SCOPE.md section 8.3). Gear and profile edits (D) and the linked-hero import (E) remain.
- **A new completion is checked in order:** the habit exists and is the player's (`invalid`), the date is within today minus 2 to tomorrow in the player's time zone (`date_out_of_range`), and the habit existed, wasn't archived or deleted, and was scheduled that day (`not_scheduled`, using game-core's `isActiveOn` and `isScheduledOn`). "Today" is the database's clock.
- **Duplicates, earliest wins:** if the habit already has an active completion that day, the incoming one is refused as `duplicate` unless it was completed earlier, in which case the stored one is undone (its reward reversed) and the incoming one takes its place; the other phone sees the undo on its next pull.

- **Undo and retries:** pushing a known completion again changes nothing; pushing it with `undone_at` set undoes it once (XP stops at the start of the level, the level never drops, gold never goes below 0), and undone never goes back. A completion that was completed and undone on the phone before it synced is stored for the record with no effect.
- **The event log:** every change to the hero goes through one function that inserts a `character_events` row (kinds `complete` and `undo` so far, keyed by the completion id, so a retry can't apply twice) and only then updates `characters`. ## D46. The sync engine core (2026-10-24)

- **P4 PR B (D45):** `src/sync/engine.ts` runs SCOPE.md section 8.3's client algorithm. Each round takes up to 100 outbox rows (oldest first, marked as sent in the same transaction, so PR A's merging never rewrites them), sends them with the cursor and this phone's device id, validates the answer with `syncResponseSchema`, and applies it with `applyResponse` (`src/sync/apply.ts`) in one transaction. Rounds repeat while the server has more to pull or the outbox has more to send, with a stop at 50 rounds. Nothing calls it on its own yet: the triggers are PR D.
- **Applying an answer:** only the outbox rows that were sent and settled (applied or rejected) are removed, so a change made during a sync stays queued. Pulled rows land in the local tables under the phone's `LOCAL_USER_ID` (D33), except rows that still have unsent changes on the phone, whose newer version wins until it is sent. Two conflicts the server settles are mirrored so SQLite's unique indexes hold: an active completion pulled from another phone marks this phone's active one for the same quest and day undone (the server keeps the earliest, D38), and a pulled item removes a local copy of the same item under another id (D39). The server's hero replaces the estimate and the cursor is stored.
- **One sync at a time:** a sync asked for while one runs joins it. A network error (`offline`) or 5xx keeps the outbox, writes the error on the sent rows and schedules a retry after 2 s, 4 s, 8 s and so on, up to 5 minutes; a 4xx (`refused`) waits for the next trigger, because retrying won't change the answer (the 409s are PR E's). Timers are injected, so the tests control them.
- **The transport** is an interface; the real one is `sendSync` in `src/lib/supabase.ts` (`functions.invoke('sync')` with the session's token), keeping network code in one place, and `syncFailure` maps its errors to offline, server or refused.
- **Sync state:** `src/db/queries/sync-state.ts` keeps the one `sync_state` row, created with a device id on first use. `deletePlayerData` now rewinds the cursor, so a new or wiped player pulls from the start.
- **Rejections are handed back** to the caller and leave the outbox; rolling them back on the phone with a toast is PR C.
- **Tests:** eleven engine tests on sql.js against an in-memory fake server (`src/test/fake-sync-server.ts`; it stores by id and numbers writes like the real one but skips the game rules, which the Deno tests cover): sending and applying (rows, rewards, hero, cursor); pulling another phone's rows page by page; one sync at a time; offline then 5xx then success with 2 s and 4 s retries; a reply lost after the server applied the changes, resent and counted once (the network cut mid-sync); a change made during a sync kept and sent next, with the phone's version kept in between; a refused sync not retried; rejections handed back; another phone's completion winning; the cursor rewound on wipe; the backoff steps. One more app test covers `syncFailure`. Not marking rows as sent, removing every outbox row, dropping the unsent-wins rule, never retrying, not joining a running sync and not storing the cursor each made a test fail.
- **Size:** about 800 changed lines, half of them tests and the fake server, over the ~400 guide; the status for the sync pill moved to PR D to keep it from growing further.

## D47. Refused changes: rollback and notices (2026-10-26)

- **P4 PR C (D45):** what the server refuses is undone on the phone and the player is told why (SCOPE.md section 8.3).
- **The rollback runs inside the transaction that applies the server's answer,** after the sent rows are settled and before pulled rows are written. A refused completion is removed; a refused purchase removes the item; a refused new quest is removed with its completions. Only rows the server never confirmed (no `server_seq`) are removed: a refused edit to a row the server already has leaves the row, so the server's version stands. Refused purchase undos and profile edits need nothing, since the server answers `applied` for those in practice. The hero needs no correction of its own: the server's hero, which replaces the estimate in the same transaction, never included the refused change, so its optimistic XP or gold disappears with it.
- **What the player is told:** one plain sentence per refusal, from `rejectionMessage` in `src/sync/notices.ts`: "That purchase failed: not enough gold." (the scope's example), "That quest was already done on another device.", "That quest wasn't due that day, so it didn't count.", "That completion was too old to sync, so it didn't count.", "You already own that item from another device.", and "A change couldn't be saved and was undone." for anything else.
- **Showing it:** notices wait in a small in-memory queue (one per distinct message, so three refused duplicates are one sentence) and `SyncNotices`, mounted at the app root over every screen, shows them one at a time with the `Toast` from packages/ui (error tone, 5 seconds, announced by screen readers). The engine still only returns its rejections; PR D's triggers will call `pushRejections` with them, so no notice can appear in the app before then.
- **Tests:** four engine tests against the fake server (a refused completion gone and the hero the server's; a refused purchase gone and the gold the server's; a refused new quest gone with its completions; a refused edit to a known quest keeping it), two notice tests (every message; the queue in order, deduplicated, telling listeners) and two component tests (nothing without a notice; one at a time for 5 seconds each). Skipping the rollback, removing rows the server confirmed, not deduplicating and never dismissing each made a test fail. On the simulator, the app still starts normally with `SyncNotices` at the root.

## D48. The first sync for an account (2026-10-26)

- **Owner decisions:** (1) the first sync (PR E) comes **before** the sync triggers (PR D), because turning syncing on for a linked hero before its import would get its new completions refused and rolled back; (2) when an account already has a hero and the phone has a different one, the player gets **both choices**: "Use my account's hero" replaces the phone's, and "Keep this phone's hero" replaces the account's game data (not the login) through a replace flag on the import, each behind a confirm. E is split: E1 (this) is the first sync, E2 the two-heroes choice.
- **A phone runs the first sync once per account** (`src/sync/first-sync.ts`): it applies while `sync_state.user_id` isn't the signed-in account. With a hero on the phone (linked, or made at onboarding after signing in) it uploads the whole history as an import (D42), built from the tables: the profile with its real start date, every quest including archived and deleted ones, then completions and purchases in the order they happened. Undone completions go as they are and count for nothing; worn gear goes as worn from its purchase. Batches are 200 changes, the request limit, and the last one is marked done. The import's refusals are rolled back like any other (D47), the outbox is cleared (the import carried it), the cursor rewinds, and a normal pull brings the server's rebuilt hero.

Without one, only once the pull worked. Before that, nothing is recorded and the first sync simply runs again.

Offline, the player goes to onboarding as before; the hero made there goes up as an import later, and if the account turns out to have a hero, that is E2's conflict. Linking an account and finishing onboarding while signed in start the first sync in the background.
- **A conflict changes nothing:** `409 hero_exists` (the server's code is now read from the refusal's body, validated with Zod) returns `conflict`, leaving the phone's hero, its outbox and the unsynced state as they were, for E2.
- **Tests:** nine tests against the fake server: the import's order and contents (archived quest, a purchase between completions, worn gear, an undone completion), when a first sync is needed, the upload then pull, 212 changes going as 200 and 12 with only the last done, a fresh phone pulling another phone's hero, the conflict, offline, synced-after-import even when the pull fails, and the import's refusals undone. ## D49. Keeping a phone's hero over the account's: the server side (2026-10-26)

- **Owner decisions:** E2 (D48) is split into E2a, the server (this), and E2b, the phone's choice. Three additions to D48 were agreed with it: phones still holding a replaced hero are told to start again; the `hero_exists` refusal names the account's hero, so the phone can show both; and only the phone that started an import may continue it.
- **`replace` on the import** (`packages/shared`) is the player's choice to keep this phone's hero. On an account with a finished hero, the server deletes the `profiles` row inside the sync transaction, behind the player lock; the hero, quests, completions, closed days, gear and event log go with it by cascade, and the login stays. The import then runs as for a new account. The request must begin with the new hero's profile, so the account is never left without one; otherwise it gets `400 bad_import` and nothing changes. `replace` does nothing on an account with no hero or during a running import, so the phone may send it on every batch.
- **Phones still holding the replaced hero:** deleted rows leave nothing for another phone to pull, so it would keep the old quests next to the new hero and push changes for quests the server no longer has. The replace draws a `sync_seq` value after every old row and before every new one and stores it as `profiles.replaced_seq` (migration `hero_replace`). An ordinary sync whose cursor is above 0 and below it gets `409 hero_replaced` and changes nothing; that phone is to wipe its player data and pull from 0 (E2b). A phone that pulls from 0, or has already pulled the new hero, syncs as usual.
- **The refusal body is part of the contract:** `syncRefusalSchema` (`error`, plus the account's `hero` with `hero_exists`: name, class and level) and `REFUSAL_CODES`. The hero is the signed-in player's own, found by the token's user id; nothing from the request is echoed.
- **One phone per import:** `characters.import_device` is the phone that started the import, cleared when it's done. Another phone's import while it runs gets `409 import_in_progress`, with or without `replace`, instead of being mixed into it.
- **Known gap, the owner's call later:** an import its phone never finishes (the app deleted mid-import) leaves the account importing for good, so ordinary syncs and other phones' imports are refused. That was already so with D42; a way out, such as letting another phone take over an import idle for some time, isn't built.
- **Tests:** five new Deno tests (64 in all). A replace removes the account's quest, completion and purchase, keeps the login, and leaves an event log that adds up to the new hero alone. A replacing import sent in two requests replaces only on the first. A phone with the old cursor gets `hero_replaced` and its change isn't applied, while one pulling from 0 gets the new hero and syncs on. A replace that doesn't start with a profile is refused and the old hero stays. Another phone can't join a running import. The `hero_exists` test now checks the hero it names, and `packages/shared` has three new schema tests. Seven mutations each made a test fail: deleting nothing, replacing on every batch, no cursor guard, not recording `replaced_seq`, not requiring the profile first, letting any phone continue an import, and leaving the hero out of `hero_exists`.
- **Next, E2b:** the phone reads the hero from the refusal, shows both heroes with "Use my account's hero", "Keep this phone's hero" and "Not now", each choice behind a confirm, sends `replace`, and on `hero_replaced` wipes its player data and pulls again.

- **Who reads what:** a party's rows are readable only by its active members, through a `security definer` `is_party_member(party)` that answers only for the signed-in account (section 8.1); a member who leaves loses access; claims are readable by their owner; `rate_limits` by nobody. Clients write nothing: inserts, updates and deletes are revoked as for the player tables (D32), and every write goes through the functions with the service role. `party_events` is in the `supabase_realtime` publication, and Realtime applies the same select policy.
- **Accounts and heroes:** membership and claims reference `auth.users`, not `profiles` (section 8.1 has `profiles`), so replacing a hero (D49) keeps the account in its party and deleting the account removes both. `party_events.user_id` has no foreign key on purpose, so a deleted member's past damage stays in the log, to be shown as a former member. A party carries on when its creator deletes their account (`creator_id` set to null). `undo` is a new event kind for the "correction event" of section 9.4.
- **Tests:** 24 pgTAP checks (68 in all): the code, name and HP rules, one party at a time, the Realtime publication, a member reading only their party's rows and only their own claims, no client writes to any party table, a member who left and an anonymous visitor reading nothing, and the account cascades. The existing schema test now lists the party tables too. Opening the battle log to everyone, keeping access after leaving, tying membership to the profile, and leaving out Realtime each made a test fail.

## D57. The `party` function (2026-10-27)

- **Owner decisions:** PR B with the four recommendations: "Party damage this week" lists active members and anyone who left after hitting this week's boss; an account with no hero can't create or join (`409 no_hero`); a player who left may rejoin the same party, reopening their membership; one PR.
- **The contract** (`packages/shared/src/party.ts`, copied for Deno): four actions, `create` (a name cleaned like hero names, 3 to 24 characters), `join` (a code in any case, normalised by game-core), `leave` and `state`; refusal codes `not_found`, `party_full`, `already_in_party`, `not_in_party`, `no_hero` and `rate_limited`; and the snapshot every action answers with: the party, its members (hero name and class, or none for a hero that no longer exists, whether active, and this week's damage net of undone completions), the latest boss with the days left in the creator's time zone, the latest 20 battle-log lines and whether this player has claimed. `claim_reward` comes with victory in PR C.
- **`create`** takes the time zone from the creator's profile, picks a code with game-core's generator and a crypto source (retrying on the rare clash), adds the creator, the first week's boss (Procrastination Slime with 500 HP, for the one member there at the start) and a `join` line. **`join`** locks the party row so two players joining at once can't make a fifth member, and keeps HP as it was set at the start of the week. **`leave`** marks the member as left and adds a `leave` line; past damage stays on the boss.
- **Rate limit:** create, join and leave count toward 10 a minute per account in a fixed one-minute window in `rate_limits`, counted in their own transaction so refused attempts count too; the eleventh gets `429 rate_limited`. Reading the snapshot isn't counted, since the phone asks for it on every Realtime event.
- **As in `sync`:** the user id comes only from the token, requests are validated with Zod, and errors return paths and codes, never the values sent. A non-member asking for `state` gets `{ party: null }`, and the snapshot is only ever built for a member's own party.
- **Tests:** six Deno tests against the stack (70 in all): what create makes; no hero, no party; joining in any case, then full, unknown and one party at a time; leaving, rejoining, and a leaver with damage staying listed; members-only answers and no echo; and the rate limit. Removing the size limit, dropping leavers with damage, keeping left members in their party, not needing a hero, and not limiting calls each made a test fail. Shared has four new schema tests.

## D58. Boss damage on sync and the reward (2026-10-27)

- **Owner decisions:** PR C with the four recommendations: the battle log records which completion dealt which damage; an imported history never hits the boss; anyone who was an active member when the boss fell may claim, for any defeated boss of their party, once; one PR.
- **Damage** (`supabase/functions/_server/boss.ts`, SCOPE.md section 9.4): when `sync` accepts a live completion from a player in a party, the same transaction locks the party's latest boss row (`for update`), and if the completion is dated in that boss's week (D56) and the boss is still up, lowers its HP with game-core's `applyBossDamage` and adds a `damage` line with the quest's name and the damage really dealt, so the last hit is cut to what was left. The hit that reaches 0 sets `defeated_at` and adds a `victory` line, stamped with `clock_timestamp()` so it sorts after the hit within the same transaction.
- **Undo:** whenever a completion is undone (by its player or as the later of two duplicates), the damage it dealt comes back with game-core's `undoBossDamage` and an `undo` line; a defeated boss stays defeated, so a victory and its rewards can't be taken away.
- **Once per completion:** migration `battle_log_completions` adds `party_events.completion_id`, unique per completion and kind, so a hit or its undo is applied at most once even if a sync is retried. It has no foreign key, so the log outlives deleted completions.
- **Imports:** `sync` passes `live = false` for an import's completions, so a hero's past, imported on linking or by "keep this phone's hero" (which keeps the party), never hits the boss; only completions made live afterwards do.
- **`claim_reward`** on `party` (`{ boss_week_id }`): refused with `not_found` (unknown boss, or never a member), `not_defeated`, `not_in_party` (joined after the victory or left before it) or `already_claimed`; otherwise one `boss_claims` row and +50 gold through `changeHero` behind the player's lock, as a `boss_reward` event whose ref names the player and the boss (character events are unique per kind and ref across players). The phone gets the gold on its next sync. It counts toward the rate limit.
- **Tests:** five Deno tests (75 in all): a hit, a retry that doesn't hit again and an undo that heals; the last hit cut short with its victory, kept after an undo; the week rule and an import that deals nothing; the race; and the reward paid once, matching the event log, refused before victory, a second time, and to a member who joined later. **The race** is staged directly against `hitBoss` in two transactions on separate connections, the first held open while the second hits: the locally served function runs one transaction at a time, so two simultaneous syncs never really overlapped, and an earlier version of this test passed without the row lock. Removing the lock, the heal, the import flag, the week check, the cut, the once-only claim or the membership check each made a test fail.
- **`pnpm sync:test`:** the local Docker stack stopped answering for a while just before it ran (as earlier on 2026-10-27), and all 52 runs failed creating their test accounts; `newAccount` now says so instead of passing an undefined id on to sql.js. Once the stack answered again, all 52 passed (50 two-phone runs and 2 first-sync tests) with boss damage in the sync function.
